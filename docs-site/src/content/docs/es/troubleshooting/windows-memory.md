---

Unos Windows usuarios ven el proceso `bun` detrás de opencodex crecer a muchos gigabytes de RSS durante largas sesiones de transmisión (reportado como el problema [#314](https://github.com/lidge-jun/opencodex/issues/314)). Esta página explica lo que realmente está sucediendo y lo que puede hacer al respecto, honestamente.

<a id="root-cause-upstream-bun-runtime-issues"></a>

## Causa raíz: problemas de entorno de ejecución Bun ascendentes

Las versiones anteriores de OpenCodex incluían Bun **1.3.14**. La tabla siguiente recoge la investigación del 23 de julio de 2026: es evidencia histórica, no el estado actual de las incidencias de Bun. El paquete actual incluye Bun **1.4.2** y el control de compatibilidad reconoce Bun estable 1.4.0 o posterior como portador de la corrección de cancelación async-pull. Esto no demuestra que se hayan resuelto todas las causas de crecimiento de memoria en Windows.

| Bun emisión | Estado (comprobado 2026-07-23) |
|---|---|
| [#28035](https://github.com/oven-sh/bun/issues/28035) - `fetch()` reciben contrapresión no acoplada al consumo de JS | Corregido por [PR #29831](https://github.com/oven-sh/bun/pull/29831); **que la liberación lleva no está verificada** - suponemos que el paquete 1.3.14 no |
| [#32111](https://github.com/oven-sh/bun/issues/32111) - se bloquea cuando un cliente aborta un flujo de asincronización-pull | Corrección [PR #32120](https://github.com/oven-sh/bun/pull/32120) fusionó 2026-06-21; no se asume presente en 1.3.14. Nota: esta caída es **no Windows -específico** (también reproducido en macOS / Linux) |
| [PR #31654](https://github.com/oven-sh/bun/pull/31654) — fuga de handles de sockets en `node:net` | Todavía **abierto** en Bun |

En entornos antiguos, Windows usaba la ruta conservadora basada en tee para evitar el fallo de cancelación async-pull; un cliente lento podía dejar datos en memoria nativa que JavaScript no podía limitar. Con el entorno estable actual, Windows selecciona el relé acotado en `auto` cuando no hace falta reescribir la respuesta para el cliente. Un `legacy-tee` explícito conserva la ruta anterior. En macOS, `auto` sigue usando tee y el relé requiere activación explícita. Comprueba el entorno seleccionado y la decisión efectiva de transmisión antes de diagnosticar el crecimiento de memoria.

<a id="what-opencodex-does-today"></a>

## Lo que opencodex hace hoy

La mitigación acotada y la observabilidad ayudan a diagnosticar la retención, pero no demuestran que todos los casos de crecimiento de memoria estén corregidos:

- **Perro guardián de la memoria**: el proxy muestrea su propia memoria cada minuto y registra una advertencia de velocidad limitada cuando la memoria observada cruza 4 GiB. La memoria observada es la más grande de RSS, `external`, y `arrayBuffers` (no su suma), porque Windows contadores del conjunto de trabajo/RSS pueden infranotificar la retención externa confirmada.
- **`ocx doctor`** — una sección "Memoria / entorno de ejecución" muestra la *servicio*
  Bun versión del proceso, RSS, contadores externos / ArrayBuffers, contexto JS-heap, y la decisión de modo de transmisión. En entornos antiguos de Bun 1.3.14, `heapUsed` /
  `jscHeap` solos no son un discriminador de fugas; compare la memoria observada con
  `responseState` y muestras repetidas antes de asignar una fuga a nivel de aplicación.
- **`GET /api/system/memory`** - los mismos datos sobre la administración autenticada API para paneles o scripts. Junto a los contadores RSS/heap/external informa de un bloque escalar `responseState` (recuento de entrada, bytes serializados totales/mayores, edad de entrada más antigua) para el almacén de continuación en memoria `previous_response_id` del proxy. Esto atribuye un crecimiento adicional: un `responseState.totalBytes` creciente bajo el aumento de los puntos de memoria observados en la retención de la conversación (cadenas largas `store:false` que se vuelven a expandir cada turno), mientras que un `responseState` plano bajo el aumento de la memoria observada se aleja de esa tienda. Los valores son solo escalares (sin cuerpos de solicitud, tokens, rutas o identificadores de cuenta) y la lectura es libre de efectos secundarios (nunca poda ni desaloja). El estado de derrame-escritura se informa por separado dentro de ese bloque: `spillWriteStatus` comienza como `initial`, se convierte en `degraded` después de una publicación fallida y vuelve a `healthy` después de la próxima publicación exitosa. `spillWriteConsecutiveFailures`, el último tiempo de fallo, y el último tiempo de éxito muestran si los fallos se están acumulando o recuperando en el mismo proceso. El último fallo es una clase fija segura para la privacidad, como `EACCES`, `ENOSPC`, `ETIMEDOUT` o `EACLRETRYEXHAUSTED`; nunca se devuelven los mensajes de error en bruto y las rutas del sistema de archivos. `spillLastWriteFailureOrigin` agrega un origen fijo o nulo: `retry_returned_timeout` significa el segundo intento de derrame existente devuelto un tiempo de espera; `timeout_memo_refusal` significa que el ayudante de ACL se negó a través de su estado de tiempo de espera recordado. Otros fallos usan null. Las publicaciones fallidas del terminal de recuento acumulativo `spillAclRetryReturnedTimeouts` y `spillAclTimeoutMemoRefusals`, no órdenes de ACL individuales o primeros intentos transitorios. Cuando una nueva continuación no cabe bajo el techo de derrame de 1 GiB, el proxy primero desaloja las continuaciones almacenadas más antiguas para hacer espacio, siempre que eso pueda tener éxito; una continuación que no puede caber incluso entonces es rechazada. El acumulado `spillHeadroomEvictions` cuenta las continuaciones desalojadas para hacer espacio, y `spillCapacityRefusals` cuenta las continuaciones rechazadas porque el techo no pudo hacer espacio (cada una también es una publicación fallida con clase `ECAPACITY`). Un aumento de `spillCapacityRefusals`, mientras que la memoria es saludable significa que el conjunto de continuación durable está lleno de espacio que el proxy no puede recuperar - publicaciones en vuelo o archivos de un borrado fallido dejado atrás - en lugar de un problema de memoria. El éxito borra la racha de fallos pero conserva los últimos campos de fallos y los recuentos acumulativos; un fallo posterior no relacionado establece el último origen en nulo. Estos valores son process-local, así que compara instantáneas del mismo proceso. Ninguno de los orígenes identifica un comando del sistema operativo: el presupuesto del intento puede caducar antes de que se inicie un comando, y una inspección de cumplimiento opcional puede ejecutarse antes de que se rechace un memo. Un proceso separado que tenga éxito no prueba que el memorándum del proceso en vivo se recuperó. Estas observaciones no agregan reintentos, borran memos, debilitan las ACL requeridas ni reinician automáticamente el servicio.

  Estos diagnósticos permanecen en el punto final de gestión autenticado y están intencionalmente ausentes de `/healthz`, que sigue siendo una señal de vitalidad. La tarjeta **Observabilidad de la memoria** del tablero de instrumentos renderiza los campos de memoria y tamaño de continuación de este punto final y ofrece una acción **Drenar y reiniciar** de confirmación: muestra el recuento de giros activos actual, espera hasta 60 s para los giros activos (reutilizando el drenaje HTTP 503 JSON `server_restarting` + `Retry-After: 5` existente), luego aborta los giros restantes. El proxy en ejecución posee la autorización de reinicio y la coordinación de drenaje, luego sale; un administrador de servicios instalado inicia el reemplazo cuando corresponde. La acción reporta el éxito solo después de que un proceso diferente verificado por identidad sea saludable en el mismo puerto, sin derribar la inyección Codex. Eso es un reciclaje más largo e informado que el drenaje corto en `POST /api/stop`.

  Para obtener una instantánea de la carga útil autenticada completa, ejecute `ocx observe memory --json`; el CLI reenvía los mismos campos de estado de respuesta.
- **Una ruta de transmisión alternativa con control de compatibilidad:** el relay de un solo lector acota el almacenamiento en búfer. En Windows, `auto` selecciona esta ruta cuando el entorno compatible y la forma de la respuesta lo permiten; `legacy-tee` conserva explícitamente la ruta tee. En macOS, `auto` mantiene tee y `eager-relay` requiere activación explícita. Verifique la decisión efectiva del entorno de ejecución seleccionado.

Los metadatos del catálogo leen el último catálogo incluido confirmado del entorno de ejecución seleccionado. Las selecciones frías o cambiadas se actualizan a través de sondas de versión/modelo asíncronas, por lo que esas sondas no mantienen el bucle de eventos proxy. Las actualizaciones compartidas tienen una fecha límite de 45 segundos; las actualizaciones activadas por solicitud fallidas conservan filas coincidentes y aplican un tiempo de reutilización de reintento de 60 segundos. Solicitar aborto libera la contabilidad del traductor incluso cuando no se lee un cuerpo de respuesta. Estos cambios de vitalidad no establecen que se resuelva la retención de la corriente nativa Windows ([#6671](https://github.com/lidge-jun/opencodex/issues/6671)).

La mejora de RSS en el mundo real de estos cambios es **Esperando la verificación de Windows usuarios** - no afirmamos que la fuga sea reparada.

El reinicio automático basado en umbral se envía deliberadamente **no**. Si el proceso falla, los administradores de servicios (Task Scheduler/WinSW, launchd, systemd) ya lo reiniciarán.

<a id="your-options"></a>

## Sus opciones

1. **Compruebe el entorno y la ruta de transmisión efectivos.** El paquete actual incluye Bun 1.4.2 y la puerta de compatibilidad acepta versiones estables desde 1.4.0. En Windows, `auto` ya puede seleccionar el relay acotado cuando corresponde; no es necesario esperar otra actualización para habilitarlo. Una selección explícita de `legacy-tee` conserva tee. Esto no demuestra que estén resueltas todas las causas del crecimiento de memoria.

2. **Ejecute un entorno de ejecución Bun en el que confíe con `OPENCODEX_BUN_PATH`.** Configure la variable antes de iniciar `ocx` desde ese shell, luego ejecute `ocx service repair` para hornear el entorno de ejecución seleccionado en la definición de servicio. Un proyecto posterior `.env` no cambia la selección; cambiar el entorno por sí solo no actualiza un servicio instalado.

3. **Seleccionar el relay acotado con `streamMode: "eager-relay"`.** Puede editar `config.json` para añadir `"streamMode": "eager-relay"` o enviar `PUT /api/settings` con `{"streamMode":"eager-relay"}`; el cambio por API se aplica a turnos nuevos sin reiniciar. El aviso de bloqueo de Bun 1.3.14 es histórico: esa versión usaba la forma de transmisión afectada por #32111 y podía fallar en cualquier sistema operativo, interrumpiendo las solicitudes activas aunque el servicio se reiniciara. `"legacy-tee"` fuerza la ruta tee anterior. En Windows, `"auto"` usa la puerta de compatibilidad y las condiciones de la respuesta; en macOS, `"auto"` conserva tee y `"eager-relay"` es la activación explícita.

Si intentas cualquiera de estos en una carga de trabajo real de Windows, por favor, informa de las secciones de memoria antes y después de `ocx doctor` en [#314](https://github.com/lidge-jun/opencodex/issues/314) - que es exactamente la verificación de esta mitigación está esperando.

<a id="windows-selected-runtime-write-refusal"></a>

## Windows rechazo de escritura en entorno de ejecución seleccionado

Windows servicio de instalación, reparación y Codex shim instalación / actualización comprobar si el ejecutable seleccionado puede crear y eliminar un directorio dentro de la raíz de configuración OpenCodex. Esta es una revisión de política de escritura, no una solución de memoria. El fallo se niega antes de que el servicio se detenga, se descargue, se ponga en escena, se escriba el token o el lanzador. La reparación automática de calzas se aplaza con la orientación y el inicio continúa. Las shims sanas o desactivadas no sondean. No se descubre ningún entorno de ejecución alternativo. Una instalación del programador por primera vez registra su tarea y reclama la raíz de configuración antes de esta comprobación; al rechazarse, se devuelve el nuevo registro y la raíz reclamada permanece para un reintento.

> El entorno de ejecución Bun seleccionado no pudo crear ni eliminar un directorio en el directorio de configuración OpenCodex. La directiva de aplicación Windows puede denegar escrituras desde esta ubicación ejecutable. Configure OPENCODEX_BUN_PATH en un ejecutable Bun de confianza permitido por su política antes de iniciar ocx, o vuelva a instalar opencodex con npm install -g bitkyc08/opencodex, luego reintente. No se seleccionó ningún entorno de ejecución alternativo.
